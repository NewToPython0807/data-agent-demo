## 2. 项目背景与目标

V2 已具备：上传数据、表/字段中文名、指标定义、复杂查询、三段式界面、导出 CSV。

V3 的目标是**从"能查"走向"查得准、查得可信"**：

- **语义更完整**：同义词、表关系（JOIN 键）、业务上下文，减少"AI 靠猜"。
- **结果更可信**：歧义先澄清、执行失败自动纠错、golden SQL 示例、结果异常提示。
- **过程可解释**：生成 SQL 前展示"分析过程/查询计划"，用户可先审思路再审 SQL。
- **质量可量化**：结果赞/踩 + golden queries 回归 + 简单统计，支撑后续迭代。

> 调研结论：SQL 生成本身已不是壁垒，**语义/上下文层与可信度**才是企业级 data agent 的核心差异。

---

## 3. 用户与使用场景

- **使用者**：公司内部小团队（5–50 人），V3 仍为**单账号**。
- **使用场景**：
  1. 维护同义词、表关系、业务上下文等语义资产。
  2. 用更口语/业务化的词提问（如"GMV""营收"），系统能正确理解。
  3. 问题有歧义时，系统先澄清，用户确认后再查。
  4. 生成 SQL 前先看"分析过程"，确认思路无误再执行。
  5. 对结果点赞/点踩，并定期跑 golden 回归，判断质量是否变差。

---

## 4. 第三版范围

### 4.1 必须完成

1. **V3-1 语义层增强**：同义词/业务术语 + 表关系（JOIN 键）+ 业务上下文（口径说明、弃用表、注意事项）。
2. **V3-2 查询可信**：歧义澄清 + 执行失败自动纠错 + golden SQL 示例库 + 结果校验/异常提示。
3. **V3-2b 查询计划展示**：生成 SQL 前输出结构化"分析过程"，前端可折叠展示，并随历史存储（单次两段：先计划后 SQL）。
4. **V3-4 评测与反馈（轻量）**：结果赞/踩 + golden queries 回归脚本 + 简单统计接口。
5. **V3-2c 超范围拒答**：对数据库与语义层均无对应数据、且无法推导的提问，**直接拒答并说明原因**，不强行生成 SQL。

**建议开发顺序**：V3-1 → V3-2 + V3-2b（含 V3-2c）→ V3-4。

### 4.2 暂不做

1. V3-3 图表可视化。
2. V3-5 数据源接入（MySQL/PG 只读）。
3. V3-6 多用户 + 基础权限。
4. V3-7 审计。
5. V3-8~11 集成（MCP/IM）、运维（监控/备份/HTTPS/CI）、知识记忆、多租户/SSO。

### 4.3 后续建议（未确认，不进入本版）

- 图表可视化、数据源接入、多用户/RBAC、审计、MCP 集成、运维自动化、分层记忆/数据图谱、多租户/SSO。
- 两次调用（计划与 SQL 分离）、候选表/指标召回（大 schema 场景）。

## 5. 功能需求

### FR-1 同义词 / 业务术语

- **做什么**：为表、字段、指标维护同义词（如"销售额 / 营收 / GMV"），问数时参与匹配与提示词注入。
- **验收标准**：用同义词提问（如"GMV 是多少"）能匹配到对应指标/字段，并生成正确 SQL。

### FR-2 表关系（JOIN 键）

- **做什么**：定义表间关联关系（如 `orders.customer_id = customers.id`），问数时注入提示词；**未定义时回退 AI 推断**（保持 V2 行为）。
- **验收标准**：已定义关系时，多表查询使用该 JOIN；未定义时仍能推断。

### FR-3 业务上下文

- **做什么**：为表/字段/指标维护业务说明、弃用标记、注意事项（如"此表已弃用，请用 xxx""口径不含取消订单"）。
- **验收标准**：弃用表/字段在提示词中被标注；口径说明被引用。

### FR-4 歧义澄清

- **做什么**：查询计划检测到关键歧义（时间范围、口径、过滤条件等）时，**先向用户澄清**；用户回答或确认按假设后，再生成 SQL。
- **验收标准**：歧义问题先出澄清；用户确认后生成 SQL；无歧义时直接生成。

### FR-5 执行失败自动纠错

- **做什么**：SQL 执行失败（语法错误、表/列不存在等）时，把错误信息反馈给模型重试（默认最多 2 次），仍失败给可读提示。
- **验收标准**：典型错误能自动纠正；重试次数可配置；最终失败有明确提示。

### FR-6 golden SQL 示例库

- **做什么**：维护"问题 → 正确 SQL"示例，问数时作为 few-shot 参考（V3 先按关键词/相似度匹配）。
- **验收标准**：示例库启用后，相似问题生成的 SQL 更贴近示例；示例可增删。

### FR-7 结果校验 / 异常提示

- **做什么**：对查询结果做基础校验（空结果、全 NULL 列、行数异常、数值量级异常），在前端给出提示。
- **验收标准**：异常结果有可读提示，不静默返回可疑结果。

### FR-8 查询计划展示

- **做什么**：生成 SQL 前，先输出结构化查询计划（指标、表、JOIN、过滤、分组、排序、假设、歧义），前端以**可折叠"分析过程"卡片**展示，并随查询历史存储。
- **验收标准**：每次问数都能看到计划卡片；历史详情可回看计划。

### FR-9 结果赞 / 踩

- **做什么**：结果区提供 👍 / 👎，记录问题、SQL、结果、评价。
- **验收标准**：点击后保存到反馈表；可被统计。

### FR-10 golden queries 回归

- **做什么**：维护 `golden_queries.json`（问题、期望结果/要点、容差），脚本执行"生成 → 执行 → 比对"并输出通过率。
- **验收标准**：脚本可运行、可重复，报告每条通过/失败。

### FR-11 简单统计接口

- **做什么**：`GET /api/feedback/stats` 返回总查询数、赞/踩、golden 通过率等。
- **验收标准**：接口返回统计；前端可在历史页展示简单统计（不做独立看板页）。

### FR-12 超范围拒答

- **做什么**：当查询计划判定问题的**核心数据**（表/字段/指标/语义）在数据库中不存在、且无法从已有数据推导时，**直接拒答**，并说明"缺少什么数据/指标"，不生成 SQL。
- **验收标准**：提问"国民经济收入是多少"时，系统返回拒答与原因，不输出 SQL；对数据库内可回答的问题不误拒。

## 6. 核心交互流程

### 6.1 问数（含计划、澄清、拒答）

1. 用户提问。
2. 系统生成**查询计划**（指标/表/JOIN/过滤/分组/排序/假设/歧义），展示为可折叠卡片。
3. **若计划判定"无法回答"（超出数据范围）→ 直接拒答并说明原因，不生成 SQL。**
4. 若计划含关键歧义 → 先展示澄清问题；用户回答或确认按假设继续。
5. 系统基于计划生成 SQL。
6. SQL 执行失败 → 自动纠错重试（有限次）。
7. 用户审核/修改 SQL → 确认执行。
8. 结果展示；若结果异常 → 提示；用户可 👍/👎。

### 6.2 语义层维护

1. 进入「数据表」/「指标」页。
2. 维护表/字段/指标的中文名、**同义词**、**业务上下文/弃用标记**。
3. 在「表关系」中维护 JOIN 键（可选，未维护则 AI 推断）。

### 6.3 评测

1. 日常使用中对结果 👍/👎。
2. 修改提示词/语义层后，运行 `python -m app.eval` 跑 golden 回归。
3. 查看统计接口/历史页小卡片，判断准确率变化。

## 7. 非功能需求（仅已确认内容）

- **数据规模**：10 万行以内（沿用 V2）。
- **轻量化**：沿用 SQLite + FastAPI + Docker。
- **单账号**：V3 仍不做多用户/RBAC。
- **部署**：沿用现有腾讯云服务器。
- 性能/并发硬指标：不设；但 V3 新增 LLM 调用（计划、纠错、澄清）会增加延迟，需在 UI 上给出"分析中"状态。

---

## 8. 数据与权限

- **数据来源**：网页上传 CSV/Excel（V3 不接数据库）。
- **存储**：SQLite（沿用）。
- **权限**：单账号（沿用）。

### 8.1 建议的数据模型变更（实现参考，可调整）

| 对象 | 变更 |
| --- | --- |
| `table_meta` | 增加 `synonyms`、`context`、`is_deprecated` |
| `column_meta` | 增加 `synonyms`、`context`、`is_deprecated` |
| `metrics` | 增加 `synonyms`、`context` |
| `table_relations`（新） | `id, left_table, left_column, right_table, right_column, description` |
| `golden_sql`（新） | `id, question, sql, tags, created_at` |
| `feedback`（新） | `id, history_id, question, sql, rating, comment, created_at` |
| `history` | 增加 `plan`（JSON 文本） |

> 迁移采用"存在则跳过"的增量方式（`ALTER TABLE ... ADD COLUMN` 前先查 `PRAGMA table_info`），不破坏 V2 数据。

### 9.2 待确认（细化项，已有默认值）

| 编号 | 事项 | 默认处理 |
| --- | --- | --- |
| D1 | 歧义"关键"的判定 | 时间范围/口径/过滤条件缺失视为关键；其余作为"假设"展示 |
