## 2. 背景与目标

V3 评测结论：**模型能力及格，产品体验不合格**。

| 指标 | V3 基线 | 说明 |
| --- | --- | --- |
| 首轮准确率 | **3.85%**（2/52） | 94.2% 的应回答问题首轮被要求澄清 |
| 最终准确率（按假设继续） | 86.54%（45/52） | 数值等价后 90.38% |
| 过度澄清率 | **94.23%**（49/52） | 澄清精确率仅 15.25% |
| 消费口径遵循率 | 89.2% / 91.9% | 漏 `is_consumption_flag='Y'`，金额放大 5 倍 |
| 比率单位一致率 | 约 96%（2/52 单位错） | 小数 vs 百分比混用 |
| 安全拦截率 | 100% | 已达标 |
| 端到端 P50 / P95 | 4.66 s / 5.98 s | 延迟主要来自模型 |
| 提示词 tokens | 5,338 / 次 | 语义层占 79.9%，9 张测试表占 23.9% |
| 指标中文/同义词命中 | 1/17 | `match_metrics` 只按英文 name 匹配 |

**V3.1 目标**：完成 P0/P1/P2 优化，首轮准确率 ≥85%、过度澄清率 ≤10%、澄清精确率 ≥80%、消费口径遵循率 100%、安全保持 100%。

## 3. 范围

### 3.1 本期完成（D7 A）

1. **P0-1 澄清分级**：只对 `blocking` 业务歧义澄清；实现细节/默认假设归入 `assumptions`。
2. **P0-2 澄清默认路径**：澄清卡片主按钮「按假设继续」，展示 `assumptions`；非阻塞歧义不打断。
3. **P1-1 消费口径强制化**：提示词硬规则 + SQL 后置校验 + 自动重试 1 次 + 告警兜底。
4. **P1-2 比率单位统一**：SQL 统一输出小数（0–1），前端按 `%` 格式化。
5. **P1-3 语义层清理（D5 B）**：**物理删除 9 张测试表 + 测试指标**，保留 14 张信用卡表与 16 个指标。
6. **P1-4 指标同义词匹配**：`match_metrics` 按 name + synonyms 匹配。
7. **P2-1 评测转 golden 回归**：80 条用例 + 过滤条件断言 + 阈值。
8. **P2-2 拒答/澄清分流**：可澄清的不要直接拒答，敏感信息直接拒答。

### 3.2 本期不做

- 多模型切换、RBAC/多用户、行/列级权限、审计、MCP/IM 集成；
- 图表、看板、订阅；
- 大 schema 的向量召回、两次调用（计划与 SQL 分离）；
- V4 规划中的其他能力。

## 5. 功能需求

### FR-1 澄清分级（P0-1，D1 A）

- **做什么**：
  1. 计划字段 `ambiguities` 由字符串数组改为对象数组：`[{"text": "...", "level": "blocking|assumption"}]`；
  2. 提示词硬规则：字段取值（Y/N、1/0）、`is_xxx_flag`、`date_key` 与业务日期选择、是否剔除冲正、默认全历史等**实现细节一律写入 `assumptions`**，不得写入 `ambiguities`；`ambiguities` 只列“存在两种以上合理解释且结果会不同”的业务问题（时间基准、指标定义、统计范围）；
  3. 代码兜底：`app/plan.py` 增加 `is_blocking(text)` 规则（关键词：时间范围/口径定义/指标定义/统计范围/维度定义等为 blocking；`is_`/flag/date_key/字段/取值/编码/代理键/入账等为实现细节）；
  4. 解析时：模型给 `level` 则采用；未给则用 `is_blocking()` 判定；旧格式字符串默认 `assumption`；
  5. `/api/ask`：只有 `blocking` 列表非空且用户未选择“按假设继续”/未补充说明时，才返回 `clarify`。
- **验收标准**：80 条回归中，首轮准确率 ≥85%，过度澄清率 ≤10%，澄清精确率 ≥80%。

### FR-2 非阻塞歧义自动继续（P0-2，D2 A）

- **做什么**：
  1. 无 `blocking` 歧义时，直接返回 SQL；`assumptions` 随计划返回；
  2. 前端「分析过程」卡片展示 `assumptions`；
  3. 澄清卡片（仅 blocking 时出现）主按钮「按假设继续（推荐）」，次按钮「补充说明」；卡片展示已识别的 blocking 歧义与 assumptions。
- **验收标准**：明确问题首轮直接出 SQL；计划卡片可见 assumptions。

### FR-3 消费口径强制化（P1-1，D3 A）

- **做什么**：
  1. 提示词硬规则：问题含“消费/交易/刷卡/金额”且未明确“取现/还款/全部交易”时，必须 `JOIN dim_transaction_type` 并带 `is_consumption_flag='Y'` 且 `is_reversal_flag='N'`；
  2. 聚合类问题必须返回聚合结果（单行或分组行），不要返回明细行（针对 C06 粒度抖动）；
  3. 后置校验 `app/caliber.py`（或 `validate.py` 新增）：识别问题消费意图 + SQL 使用 `fct_transaction` 但缺 `is_consumption_flag` → `missing_caliber`；
  4. 缺失时自动重试 1 次：用纠正提示把问题、原 SQL、缺失条件反馈给模型；重试后仍缺失 → 返回 `warnings`（不阻断），前端提示。
- **验收标准**：消费口径遵循率 100%；N19/C04 金额不再放大 5 倍。

### FR-4 比率单位统一（P1-2，D4 A）

- **做什么**：
  1. 约定：`unit=%` 的指标与比率类结果，SQL 统一输出**小数（0–1）**；
  2. 提示词规则：“比率类结果输出小数（0–1），不要乘 100”；
  3. 前端结果区对 `unit=%` 的列/指标按百分比格式化（×100，保留 2 位小数）；CSV 导出保留原始小数（避免二次转换）。
- **验收标准**：M06/C01 不再出现单位错；同一指标跨问题一致。

### FR-5 语义层清理（P1-3，D5 B）

- **做什么**：
  1. **物理删除 9 张测试表**（若存在）：`test_sales`、`test_customer`、`cons`、`big`、`e2e_sales`、`customers`、`orders`、`products`、`regions`；
  2. 删除它们在 `table_meta`、`column_meta`、`table_relations` 中的元数据；
  3. 删除 `test_sales` 的“销售额”测试指标（含 `metric_history`）；
  4. 清理 `golden_queries.json` 中引用 `test_sales` 的用例；
  5. 16 个信用卡指标补中文同义词（消费金额/交易金额、发分、用分、不良率、循环信用、户均授信等），修正单位；
  6. 语义层只保留 14 张信用卡表 + 16 个指标。
- **验收标准**：语义层表数 14、指标数 16；提示词 tokens 下降 ≥20%（目标 ≤4,200）。

### FR-6 指标同义词匹配（P1-4）

- **做什么**：
  1. `match_metrics` 同时匹配 `name` 与 `synonyms`（支持中英文逗号分隔）；
  2. `resolve_metric_question` 的裸指标快路径同样支持 synonyms；
  3. 匹配时去重、按指标名长度优先（避免子串误匹配）。
- **验收标准**：说“发分”“不良率”“循环信用”“户均授信”可命中对应指标；指标中文命中 17/17。

### FR-7 澄清卡片体验（P2-2，并入 P0-2）

- **做什么**：
  1. 澄清卡片主按钮「按假设继续（推荐）」；次按钮「补充说明」；
  2. 卡片展示 blocking 歧义 + `assumptions`；
  3. 点击继续后以 `accept_assumptions=true` 重问；补充说明以 `clarification` 重问；
  4. 补充内容写入 `plan.assumptions` 并在卡片展示。
- **验收标准**：一次点击即可拿到答案；assumptions 可见。

### FR-8 拒答/澄清分流（P2-2）

- **做什么**：
  1. 可澄清的范围/指标缺失（如“重点地区”“帮我看看数据”）→ 返回 `clarify`，不直接拒答；
  2. 敏感信息（身份证号、完整手机号、密码、完整卡号）→ 直接 `refused`，不澄清；
  3. 提示词增加分流规则；代码增加敏感意图检测兜底。
- **验收标准**：B09/B11 类澄清；R09 类拒答。

### FR-9 评测转 golden 回归（P2-1）

- **做什么**：
  1. 将 `eval_v2/cases_v2.json` 的 80 条用例转为 golden 用例（含问题、参考 SQL、期望状态、容差、`must_contain` 过滤断言）；
  2. 新增 `golden_sql_v3_1.json`（或扩展 `golden_queries.json` schema）；
  3. 新增 `run_golden.py`：逐条调用 `/api/ask`（首轮 + 按假设继续），统计首轮准确率、过度澄清、澄清精确率、安全、P95；
  4. 阈值：首轮准确率 ≥85%、过度澄清 ≤10%、澄清精确率 ≥80%、安全 100%、P95 ≤8s；不达标返回非 0。
- **验收标准**：`run_golden.py` 可跑、按阈值判定；结果落盘。

### FR-10 造数与口径对齐（D6 A）

- **做什么**：
  1. 重写 `seed_credit_card.py` 的账单/还款生成逻辑：
     - `fct_billing_cycle` 的 `new_purchase_amount`、`cash_advance_amount`、`fee_amount`、`interest_amount` 由该账户在该周期的交易汇总派生；
     - `beginning_cycle_balance` = 上一期 `closing_cycle_balance`；
     - `total_statement_amount` = 上期 + 本期四项；
     - `fct_repayment` 按账单周期生成，`repayment_amount - overpay_portion` ≤ 该期应还；
     - `closing_cycle_balance` = 应还 - 已还（可为负）；
  2. 指标修正：
     - `write_off_rate` 改为 `SUM(write_off_amount_mtd) / SUM(outstanding_balance)`；
     - `repayment_rate` 保持 SUM/SUM，校验结果在 0–100%；
     - 新增 `cash_advance_amount`（取现金额）指标：`SUM(txn_amount_cny)`，过滤 `txn_type_code='CASH_ADV'` 且 `is_reversal_flag='N'`，表 `fct_transaction`；
     - `avg_credit_limit` 明确“按账户、期末快照”，补同义词“户均授信/平均授信额度”；
  3. 重新造数并同步本地/云端；`seed_check.py` 增加指标合理性检查（write_off_rate/repayment_rate 在 0–100%）。
- **验收标准**：`write_off_rate`、`repayment_rate` 在 0–100%；N10 取现结果与交易表一致；S06 户均授信按账户。

## 6. 核心流程（V3.1）

1. 用户提问；
2. 生成计划 + SQL；解析 `ambiguities` 为 `{text, level}`；
3. 若有 `blocking` 且用户未选择按假设继续/未补充说明 → 返回澄清（卡片展示 blocking + assumptions）；
4. 否则直接返回 SQL；`assumptions` 在计划卡片展示；
5. 消费意图校验：缺 `is_consumption_flag` → 自动重试 1 次；仍缺失 → `warnings`；
6. 用户审核 SQL → 执行 → 结果；
7. 比率列按 `%` 展示（前端），CSV 保留小数；
8. 结果异常提示、赞/踩、历史照旧。

## 7. 数据与兼容性

- **API 变更**：`/api/ask` 的 `plan.ambiguities` 由字符串数组变为对象数组；旧历史数据中的字符串在解析时归一为 `{text, level:"assumption"}`；
- **前端**：计划卡片、澄清卡片、结果区需适配对象结构与 assumptions；
- **数据**：D5 B 会物理删除 9 张测试表；如后续需要演示数据，可重新运行 `seed_data_v2.py`（仅恢复 4 张演示表，语义元数据需重新维护）；
- **金标准**：`golden_queries.json` 中 `test_sales` 用例删除；
- **云端**：V3.1 上线前需重新造数（账单/还款口径对齐）并清理测试表。

## 8. 非功能需求

- **延迟**：端到端 P95 ≤8s；P50 目标 ≤3s（减少一次澄清后自然下降）；
- **成本**：单次 ask 提示词 tokens 目标 ≤4,200（清理语义层 + 压缩提示词）；
- **稳定性**：同一问题两次运行结果一致率 ≥95%；
- **安全**：写操作/提示注入/敏感导出拦截率 100%；
- **兼容**：V3 历史记录可正常回看（`ambiguities` 字符串兼容）。
